## 1. 术语表

| 术语 | 定义 |
|---|---|
| 宠记 / PetLog | 产品名。面向多宠家庭的「健康记录 + AI 健康解读 + 护理提醒」移动端应用 |
| 毛孩子 | 用户对宠物的亲昵称呼，产品内统称宠物；当前内置 2 只：小白（英短猫）、豆豆（柯基犬） |
| 铲屎官 | 用户（宠物主人）在产品内的身份称呼 |
| 今天 / 记录 / 我的 | 底部三个一级 Tab（`data-screen`：home / records / mine） |
| 健康记录 | 一次具体发生过的事项，如驱虫、洗澡、剪指甲、体重等，**带发生时间**，是真实历史数据 |
| 提醒（待办） | 未来/当天「需要做」的护理事项，可标记完成；驱动日历**灰点** |
| 纪念日 | 周期性日期（生日、到家日等），按每年月/日标记；驱动日历**粉点** |
| 三色点 | 日历格子上的状态标记：灰点=待办、绿点=健康记录、粉点=纪念日 |
| AI 健康简报 | 首页「判断层」模块：把护理/吃饭/喝水/体重四维数据翻译成健康结论，只解读不执行 |
| 今日待办 | 首页「执行层」模块：逐条列出今天要处理的护理任务并可一键处理 |
| 今日吃饭饭 | 首页「执行层」模块：只负责采集吃/喝数据，不输出健康结论 |
| 要闻 | 简报内的可点击结论条目，点击后平滑滚动/跳转到对应操作区（导诊，不越界执行） |
| 记一笔 | 统一记录表单，支持「新建今日 / 补记历史 / 编辑旧记录」三种模式复用 |
| 一键记录 | Hero 区高频护理快捷按钮（刷牙/剪指甲/铲屎/玩耍等），点按即记 |
| AI 速记 | 记一笔内的多模态录入方式：语音、拍药板/病历、拍照估体况、文字 |
| 能不能吃 | 食物安全查询工具，按物种给出「可吃 / 需注意 / 禁食」三级结论 |
| APP_TODAY | 原型演示锚点日期，固定为 `2026-09-07 12:00`，所有"今天/明天/本周"判断与日历都基于它，保证演示稳定 |
| Store | 前端本地持久化数据层（localStorage），当前有 RecordStore / ReminderStore / MemoStore 三个 |
| 种子数据 | 首次运行注入 localStorage 的演示数据（14 条历史记录等），之后可被用户增改删 |
| 真实闭环 | 有真实数据读写、状态变更、跨模块联动且刷新不丢失的交互 |
| 演示占位 | 仅有页面/点击 toast 反馈、无真实数据落库的交互（待后续建设） |

## 2. 背景、目标与边界

### 2.1 产品一句话定位

> **你负责爱它，剩下的交给宠记。**

宠记不是一个被动的"记账本"，而是一个以 AI 为核心的宠物健康管家：用户低成本地**记录**（说一句/点一下/拍一张），系统持续地**解读**（数据意味着什么健康风险），并在对的时间**提醒执行**（今天该做什么）。

### 2.2 目标用户与核心场景

| 维度 | 说明 |
|---|---|
| 目标用户 | 养猫/狗的多宠家庭主人，愿意科学养宠、但缺乏专业判断、且记录耐心有限 |
| 核心痛点 | ① 护理周期记不住（驱虫/疫苗/体检何时做）；② 看不懂数据（体重、吃饭异常意味着什么）；③ 记录太麻烦坚持不下来；④ 多宠信息混在一起 |
| 核心价值 | 录入极低成本（多模态速记）+ AI 把数据翻译成健康结论 + 护理到期主动提醒 + 多宠档案隔离 |

### 2.3 Goals（本期要做到）

| # | 目标 | 验收要点 |
|---|---|---|
| G1 | **记录全链路闭环**：健康记录可新增、补记历史、编辑、删除，列表/日历/首页四处联动 | 任意入口增改删后，日历绿点、时间线分组、首页计数同步刷新，刷新页面不丢 |
| G2 | **日历三色点全部真实**：绿点（记录）、灰点（提醒）、粉点（纪念日）均由真实数据驱动 | 新建提醒→灰点；新建纪念日→粉点；完成/删除后点消失或降级 |
| G3 | **AI 健康简报定位清晰**：只做跨模块健康"判断/解读"，不直接执行护理任务 | 简报与今日待办不重复出任务/处理按钮；要闻只做导诊跳转 |
| G4 | **吃/喝数据采集闭环**：今日吃饭饭可记三餐+加餐与喝水次数，联动简报与首页 | 点碗/餐次 chip/记一次均真实写记录并更新进度 |
| G5 | **AI 工具体系可体验**：健康管家对话、能不能吃、护理计划、报告、OCR/BCS/语音入口可达 | 各 AI 意图能进入对应流程并给出结构化反馈 |
| G6 | **多宠隔离**：小白/豆豆数据、日历、待办、体重按宠物切换独立呈现 | 切换宠物后全模块数据随之切换 |
| G7 | **无"点不动"的假按钮**：暂未实现真实业务的页面也必须有明确反馈 | 占位按钮给 toast，不出现点击无响应 |

### 2.4 Non-Goals（本期明确不做）

| # | 不做项 | 原因 / 后续 |
|---|---|---|
| N1 | 不做后端服务、账号体系、云端同步、多设备数据共享 | 当前为纯前端原型，数据仅存本机 localStorage |
| N2 | 不做真实 AI 模型推理 | AI 解读/分类/OCR/BCS/语音均为规则模板与模拟结果，验证交互而非算法 |
| N3 | 不做真实支付、会员权益核销、线上挂号交易 | 会员订阅、预约、附近医院为展示/占位 |
| N4 | 不做家庭成员协同编辑、邀请加入的真实账号流 | 家庭成员页为展示/占位 |
| N5 | 不做数据真实导出文件下载、推送通知、短信 | 导出/通知设置为占位 |
| N6 | 不做宠物品种库、宠物档案的云端持久化与账号同步 | 已支持会话内新增宠物并全站联动（刷新不保留，HOME_PETS 为内存数据）；无品种联想库 |
| N7 | 不做农历纪念日、复杂重复规则（如"每两周"）的真实排期引擎 | 纪念日按"每年同月日"标记；提醒重复字段记录但不做未来实例展开 |

## 4. 全局设计原则

### 4.1 首页三层职能切分（核心产品决策）

首页从上到下严格分为三层，解决"简报和待办功能重复"的问题：

| 层 | 模块 | 职能 | 动作边界 |
|---|---|---|---|
| 判断层（读） | AI 今日健康简报 | 整合护理/吃饭/喝水/体重四维，回答"这意味着什么健康风险" | **只解读、不执行**；要闻点击仅做导诊跳转 |
| 执行层（做） | 今日吃饭饭 | 采集吃/喝数据 | 只负责记吃/喝，不给健康结论 |
| 执行层（做） | 今日待办 | 逐条处理护理任务 | 唯一的护理"处理/完成"入口 |

**要闻导诊路由规则：**

| 要闻维度 | 点击后去向 |
|---|---|
| 护理（驱虫/疫苗等待办） | 滚动到「今日待办」 |
| 吃饭 / 喝水 | 滚动到「今日吃饭饭」 |
| 体重 | 打开体重趋势 / 报告 |

### 4.2 三色健康分级视觉

简报风险等级与配色统一：

| 等级 | class | 颜色 | 含义 |
|---|---|---|---|
| 高危 | lv-danger | 红 | 已逾期/明确风险（如驱虫空档超期） |
| 警示 | lv-warn | 橙 | 待处理/需关注（如今日未进食） |
| 健康 | lv-good | 绿 | 状态良好 |

### 4.3 日历三色点优先级

同一日期命中多类数据时，只显示优先级最高的一种点：

```
绿点（健康记录） ＞ 粉点（纪念日） ＞ 灰点（待办/提醒）
```

图例固定为：灰=待办、绿=记录、粉=纪念日。

### 4.4 统一时间锚点

所有"今天/昨天/本周/逾期"文案、分组、日历高亮、提醒日期换算，统一基于常量 `APP_TODAY = 2026-09-07 12:00`，**不使用浏览器真实 `new Date()` 做业务判断**，保证演示可复现。正式上线时该锚点应替换为真实当前时间（见 §11 待确认）。

### 4.5 移动端触摸兼容

所有自定义可点元素统一通过 `bindTap` 做 `touchstart/touchmove/touchend` + `click` 双轨绑定，规避移动端合成点击延迟/不触发问题。

## 5. 功能需求详述

### 5.1 今天 Tab

#### 5.1.1 宠物切换

- 顶部 `home-pet-switch` 提供小白/豆豆切换；切换后 Hero、简报、吃饭饭、待办、日历数据全部联动。
- 数据按 `petKey`（cat/dog）隔离。

#### 5.1.2 Hero 卡

| 元素 | 说明 | 数据/交互 |
|---|---|---|
| 问候语 | 按时段（凌晨/早/午/晚）变化 + 宠物名 | 真实时间函数 |
| 健康一句话 | 如"我已经 7 天没有驱虫啦" | 来自宠物配置 `line` |
| 今日已记（笔） | 点击进记一笔 | 真实计数 |
| 连续打卡（天） | 展示连续记录天数 | 配置值 `streak` |
| 今日待办（项） | 点击进待办页 | 真实计数 |
| 本周节奏 | 文案 + 七天圆点 | 点击进待办 |
| 一键记录 | 高频护理快捷按钮 | 点按即写一条记录并 +1；猫为刷牙/剪指甲/铲屎/玩耍，狗为遛狗/便便/洗澡/剪指甲（按物种变化） |
| 编辑 | 可管理快捷项 | 演示 |

#### 5.1.3 AI 今日健康简报（判断层）

**输入数据源（四维度）：**

| 维度 | 数据来源 |
|---|---|
| 护理 | 待办/提醒状态（是否逾期、是否有待处理） |
| 吃饭 | 今日餐次记录数（RecordStore 中 meal/breakfast/lunch/dinner/snack） |
| 喝水 | 今日喝水次数 |
| 体重 | 宠物体重序列近 3 月变化率 |

**输出结构：**

1. 报头：AI 健康管家 · 今日健康简报 · 日期
2. 今日头条：当天最值得关注的一条结论（标题 + 分级标签）
3. 要闻列表：四维各一条"健康解读"文案（不是数据播报）
4. 底部主按钮：「问管家怎么处理」→ 打开 AI 管家
5. 脚注："点要闻可直达对应记录，护理执行在下方今日待办"

**文案规则（关键）：** 从"数据播报"改为"健康解读"。
- 反例：`今天还没记吃饭`
- 正例：`今天还没有进食记录，食欲与肠胃需要关注`

每条要闻必须说清"这数据对宠物健康意味着什么"，并按风险分级配色。

#### 5.1.4 今日吃饭饭（执行层 · 饮食专项）

定位：**只采集吃/喝数据，结论统一由简报给出**，不与 AI 管家冲突。

| 功能 | 交互 | 结果 |
|---|---|---|
| 点碗记一餐 | 点饭碗插画 | 写入一餐记录，碗内粮动画、餐数 +1、进度条变化 |
| 餐次 chip | 早餐/午餐/晚餐/加餐 四个 | 点按切换该餐完成态，独立记录 |
| 喝水 | 「＋记一次」 | 喝水次数 +1，圆点进度增加 |
| 能吃啥 | 右上角入口 | 进入「能不能吃」查询 |
| 文案反馈 | 副标题/提示语随餐数变化 | 如"还没开饭哦"→"已开饭" |

手绘风：饭碗为 SVG 手绘描边风格，与全站萌系手绘视觉一致。

#### 5.1.5 今日待办（执行层 · 护理）

- 列出当天待处理护理任务（来自静态护理周期 + 自定义提醒）。
- 每条：图标、标题、描述、状态标签、处理动作。
- 「处理」按任务类型分流：
  - `kind=do`（直接做，如驱虫）→ 进入处理页，记一次后标记完成并写一条健康记录。
  - `kind=book`（需预约，如疫苗/体检）→ 进入预约页（本期占位）。
- 完成后从待办移除并联动首页计数、简报、日历灰点。

### 5.2 记录 Tab

#### 5.2.1 事项记录 / 成长记录 双视图

顶部分段切换；默认事项记录。

#### 5.2.2 分类筛选

### 5.10 宠物档案与建档（本轮重构）

#### 5.10.1 核心决策：生日与年龄不分开存

二者是同一信息的两种表达，若同时让用户填两个字段，必然出现"对不上、改一处漏一处"。统一规则：

- **只存出生日期 `birthISO`**；**年龄不入库，展示时实时计算**（按统一时间锚点 APP_TODAY 换算满年月）。
- 录入提供二选一分段（`知道生日` / `只知道约几岁`），最终都归一为 `birthISO`：
  - 知道生日 → 选日期，系统自动算年龄；
  - 只知道约几岁 → 选「岁 + 个月」，系统按锚点反推估算日期，置 `birthApprox=true`。
- 展示规则：`birthApprox=true` 时年龄与日期均带「约」「（估算）」（豆豆即此情形）；以后知道准确日期可随时改回。
- 年龄展示粒度：未满 1 月 →"未满 1 个月"；不满 1 岁 →"X 个月"；整岁 →"X 岁"；否则 →"X 岁 X 个月"。
- 日期选择器 `max` 锚点当天，禁止未来日期。

#### 5.10.2 分层建档（降低首步门槛）

建档页（pg-onboarding）按"必填 / 选填"分层，**只需 4 项即可建档**，其余之后在档案页补：

| 分层 | 字段 | 控件 | 必填 |
|---|---|---|---|
| 基础 | 名字 | 文本 | ✅（空值拦截 + toast） |
| 基础 | 种类 | 猫/狗手绘 SVG 二选一，联动顶部头像与品种占位 | ✅（默认猫） |
| 基础 | 性别 | 男生/女生 cell | ✅（默认男生） |
| 基础 | 出生日期 | 日期 / 约龄分段二选一 | ✅ |
| 选填 | 品种 | 文本，可留空 | ⛔ |
| 选填 | 绝育情况 | 已绝育 / 不清楚 / 未绝育 三选一，默认"不清楚" | ⛔ |
| 选填 | 体重 | 数字 + kg 单位 | ⛔ |
| 选填 | 到家日期 | 日期 | ⛔ |

种类图标为内联手绘 SVG（`#i-cat-face` / `#i-dog-face`），跟随选中态变色，替代风格不统一的系统 emoji。

**提交即建档（真实闭环）：** 点击"建立档案"后，表单数据构造为新宠物对象写入 `HOME_PETS`（key 自动生成 `pet3/pet4…`），自动切为当前宠物并关闭引导。新宠物的默认运行态：按物种给一键记录项（猫：刷牙/剪指甲/铲屎/玩耍；狗：遛狗/便便/洗澡/剪指甲）、无演示护理待办（待办区显示空态"今天的待办都搞定啦"）、无体重趋势序列（填了体重则生成单点，显示"再记几次看趋势"）、无连续打卡。全站四个宠物选择器（首页胶囊、记一笔、新建提醒、添加纪念日）与毛孩子管理列表统一由 `HOME_PETS` 数据驱动渲染，新宠物自动出现。

> 注意：HOME_PETS 当前为内存数据，新增宠物在**会话内**全站联动但刷新后不保留（云端持久化见 N6 / Stage 1）。

#### 5.10.3 档案详情页信息结构（pg-pet-detail）

旧版把所有信息压在头部一行（"品种·性别·年龄·已绝育·生日…"），本轮拆分为分层卡片，全部由 HOME_PETS 数据驱动渲染：

1. **顶部 Hero**：头像（可更换/AI 生成/上传）+ 名字 + 一行摘要（品种 · 性别 · 年龄，年龄自动）。
2. **基础资料卡片**（新增，查看态逐行展示；右上「编辑」进入编辑态可整体改并保存回写）：
   种类 / 品种 / 性别 / 出生日期（估算带标记）/ 年龄（标注"自动计算"）/ 绝育情况 / 体重 / 到家日期；空值统一显示"未填写"占位。
3. **纪念日**：生日、到家纪念日的日期与倒计时由 `birthISO`/`adoptISO` 实时计算（如"距下次生日 X 天""已陪伴 X"）。
4. **健康概览 / AI 养护建议**：保留；其中体重"最近记录"、健康报告卡（rp-breed）、AI 养护建议页头部摘要均改为读取结构化档案字段，不再写死。

档案编辑保存后，档案页、毛孩子列表、健康报告卡、AI 建议页头部随数据联动更新（单数据源）。

| remind | boolean | 是否开启提醒 |
| repeat | string | 每年/每月/仅一次等 |

方法：`list / monthDays / listDay(m0,day) / add / remove`。

### 6.5 日历点合成规则（伪代码）

```
recDays  = RecordStore.monthRecordDays(pet, y, m)      // 绿
todoDays = 静态 todoDates[m+1] ∪ ReminderStore.monthDays(pet,y,m)   // 灰
memoDays = 静态 memoDates[m+1] ∪ MemoStore.monthDays(pet,y,m)       // 粉
某日点 = rec ? green : memo ? pink : todo ? gray : 无
```

## 7. 关键设计点与方案对比

### 7.1 简报与待办功能重叠如何切分

| | 方案 A：简报直接出任务+处理按钮（旧） | 方案 B：分层——简报只判断，执行收敛到操作区（选定） |
|---|---|---|
| 交互 | 简报里就能点"处理" | 简报给结论，要闻点击只跳转到对应操作区 |
| 优点 | 路径短一步 | 职责单一、不重复、认知清晰；简报可持续只读、不干扰执行 |
| 缺点 | 与今日待办重复出任务，用户困惑"该在哪处理" | 多一次滚动跳转 |
| 结论 | 弃用 | **选 B**：判断层/执行层分离，用"要闻导诊"补回路径短的优势 |

### 7.2 记录编辑/补记的表单复用

| | 方案 A：新建、编辑、补记各做一套表单 | 方案 B：单表单三态复用（选定） |
|---|---|---|
| 优点 | 各自独立简单 | 代码集中、行为一致、维护成本低 |
| 缺点 | 三倍代码、易不一致 | 需维护 mode 状态与预填/来源页回退 |
| 结论 | — | **选 B**：`openRecordForm({mode,editId,date,fromDay})` 统一入口 |

### 7.3 数据持久化方式

| | 方案 A：全部写死在 HTML | 方案 B：localStorage Store + 首次种子注入（选定） | 方案 C：后端+数据库 |
|---|---|---|---|
| 优点 | 零逻辑 | 可增改删、刷新不丢、无需后端即可演示完整闭环 | 可跨端同步、多用户 |
| 缺点 | 不能交互、演示假 | 仅本机、清缓存即失 | 需要服务端/账号，超出原型阶段 |
| 结论 | 弃用 | **选 B**（当前阶段） | 正式产品演进方向 |

### 7.4 日历点数据来源

| | 方案 A：纯静态日期表 | 方案 B：静态 + 真实 Store 合并（选定） |
|---|---|---|
| 优点 | 实现最省事 | 保留演示节奏，又能真实联动用户新增数据 |
| 缺点 | 用户新增无反馈 | 需做并集与优先级 |
| 结论 | — | **选 B**：静态演示数据兜底 + 用户数据实时合并 |

### 7.5 记录时间的处理

曾出现缺陷：编辑时用 `dayStart` 丢弃时分、保存写死 12:00，导致 16:00 记录被改成 12:00。
**定稿：** 表单状态持有 `timeMin`，编辑态从原 `ts` 回填时分，新建默认 12:00，保存时 `dayStart(date) + timeMin`，不篡改原始时间。

### 7.6 占位按钮的处理

| | 方案 A：不渲染未完成按钮 | 方案 B：渲染但点击 toast 说明（选定） |
|---|---|---|
| 优点 | 不误导 | 原型可完整走查全部信息架构，点击都有反馈 |
| 缺点 | 信息架构不完整 | 用户知道是演示 |
| 结论 | — | **选 B**：统一事件委托，仅作用于覆盖式子页内"无 id/无 data 属性"的裸按钮，首页真实按钮与记一笔表单排除，避免误伤 |

| 项 | 规范 |
|---|---|
| 整体风格 | 萌系手绘风（Moe）：奶油底色、圆角卡片、手绘描边 SVG 图标、柔和粉/橙/蓝绿配色 |

## 9. 异常与边界处理（前置）

| 场景 | 处理 |
|---|---|
| localStorage 不可用/JSON 损坏 | try/catch 兜底为空对象，应用不崩 |
| 首次进入无数据 | 自动注入种子数据；列表/日历有空态 |
| 存储版本升级 | key 带版本号（records v3），升级后重新注入干净种子 |
| 记录日期非法/为空 | 正则校验 `YYYY-MM-DD`，非法 toast 提示并保留原选择 |
| 记录选了未来日期 | 记录场景拦截（提醒场景允许未来） |
| 提醒/纪念日名称为空 | toast 拦截，不保存 |
| 自定义日期 prompt 取消 | 回退到默认 chip，不残留错误状态 |
| 编辑记录时分丢失 | 用 timeMin 回填，已修复（见 7.5） |
| 删除不存在的 id | remove 按 id 过滤，幂等无副作用 |
| 元素 id 冲突 | 记录详情用 `rec-rd-*` 前缀与提醒详情区分 |
| 占位事件委托误伤 | 限定覆盖式子页 + 排除首页/记一笔/带 id 或 data-* 的真实按钮 |
| 食物查询未命中 | 别名归一 + 模糊匹配后仍无 → 提示未收录、建议咨询兽医 |
| 多宠数据串扰 | 所有 Store 方法强制传 petKey，日历/列表按当前宠物渲染 |
| 演示时间与真实时间 | 统一 APP_TODAY 锚点，避免演示随运行日漂移 |

## 10. 真实闭环 vs 演示占位（评审重点）

### 10.1 已实现真实闭环（可增改删/联动/持久化）

## 11. 待确认问题（[待确认]）

1. **时间锚点上线策略**：APP_TODAY（2026-09-07）仅为演示，正式版如何切换为真实时间？是否保留"演示模式"开关？
2. **AI 结论的责任边界**：健康解读是否需要免责声明/兽医审校机制？风险分级阈值（如体重增速、驱虫空档天数）由谁定义与维护？
3. **提醒重复引擎**：本期只存重复规则、不展开未来实例。正式版是否需要本地通知 + 实例化排期？支持哪些粒度（含农历、每两周）？
4. **数据上云规划**：三个 localStorage Store 到后端表/账号体系的迁移与多设备同步方案与时点。
5. **多宠上限与物种**：是否支持超过 2 只、猫狗以外物种（兔、鸟等），会影响分类网格与食物库。
6. **能不能吃食物库**：首发收录量级、内容审校来源（兽医/权威资料）、未命中时的兜底策略。
7. **家庭成员权限模型**：谁能增改删记录/提醒，是否区分只读与协作。
8. **会员权益边界**：哪些 AI 能力（OCR/BCS/报告/照相馆）纳入付费。
